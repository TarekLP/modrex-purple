### Rust backend modules (`src-tauri/src/commands/`)

**App startup sequence** (`src-tauri/src/lib.rs` setup hook, fires before the window shows): `migrate_from_electron` runs synchronously first, then fire-and-forget: `cleanup_thumbnail_cache` and the `mod_index` download/TTL refresh.

**Logging**: `tauri_plugin_log` writes to `Modrex.log` in the app's log dir (`%LOCALAPPDATA%\Modrex\logs\` on Windows — note this differs from `app_data_dir()`'s `%APPDATA%\Modrex\` used for `settings.json`/`mod-index.db`), level `Warn` globally and `Info` for the `modrex_lib` crate, 5 MB with one rotated backup kept. Reachable in-app via Settings > Logs ("Open log file", which copies it to `%TEMP%\modrex_log.txt` first). `install_mod`/`install_file` log every error path via `log::warn!` (not just the final install/state-write phase) so a failed install/update is always diagnosable from the log — when adding a new `?`-early-return inside either function, route it through the same log-then-return pattern rather than a bare `?`.

- **`settings.rs`** — reads/writes `settings.json` in Tauri's `app_data_dir()` (`%APPDATA%\Modrex\` on Windows, `~/.config/modrex/` on Linux). Top-level fields: `skipFileOpenLogWarning?` (global flag, PD3-only — see TopBar), `dismissedDepsWarnings?`, `games: Option<HashMap<String, GameSettings>>`. `GameSettings` holds `game_path?`, `launcher?`, `launch_options?`, `suppress_crash_reporter?` per game. Legacy flat fields (`game_path`, `launcher`, `launch_options`) carry `#[serde(skip_serializing, default)]` so old settings files still deserialize but writes always use the new `games` map. `migrate_settings(s: Settings) -> Settings` promotes legacy flat fields to `games["pd3"]` on first read — called inside `read_settings`. `game_settings<'a>(s, game_id) -> Option<&'a GameSettings>` is the canonical helper for reading per-game config; always use it instead of touching legacy fields directly. Commands: `get_game_settings(game_id: String) -> GameSettings` (new); `set_game_path`, `set_launcher`, `set_launch_options`, `configure_game_path`, `installed_launchers`, `auto_detect_game`, `set_suppress_crash_reporter` all accept `Option<String> game_id` defaulting to `"pd3"` for backwards compatibility. On first launch after the Electron-to-Tauri migration, `migrate_from_electron` copies `settings.json` and `mod-index.db` from the old Electron path (`%APPDATA%\PD3 Mod Manager\` on Windows, `~/.config/pd3-mod-manager/` on Linux). Called from `lib.rs` setup hook before the window shows.

- **`api.rs`** — modworkshop REST API via `reqwest` (Cargo features `gzip`+`brotli` negotiate response compression — ~5x smaller payloads, e.g. a 24-mod listing page is 115 KB raw vs 21 KB brotli, verified live; no code involved beyond the `Cargo.toml` feature flags). Params sent as query string (GET requests). `get_mod` returns extra fields (`images`, `banner`, `dependencies`, `instructs_template`, `tags`) absent from `list_mods` results; `list_mods` also accepts a repeated `ids[]` param (`ListModsParams.ids: Option<Vec<u32>>`) — an undocumented modworkshop feature, verified live (`/games/{id}/mods?ids[]=A&ids[]=B` returns exactly those mods, list-item shape) — that turns a bulk metadata refresh into one request per ~50 ids instead of one `get_mod` per id; see `fetchInstalledModsMeta` in `modCache.ts`. modworkshop enforces **90 req/min per IP, shared across every endpoint** (read from the `x-ratelimit-limit`/`x-ratelimit-remaining` response headers — not documented anywhere by modworkshop, and there's currently no API-key tier to request a higher one). Three-layer request control: (1) `RATE_LIMITER` token bucket (burst 4, 1.3 req/s sustained ≈ 78/min — deliberately under the real 90/min, not over it: an earlier burst-8/4-per-sec version was 2.7x over and self-inflicted 429s); (2) `RATE_REMAINING`, an `AtomicI64` updated from `x-ratelimit-remaining` on every response (success or 429) — when it reads ≤ 5, `api_get` adds a flat 3 s pause before the next send, so the client backs off proactively instead of only reacting after a 429 already happened; (3) `API_SEMAPHORE` caps concurrent in-flight requests at 3. On 429 the semaphore permit is released and the request is retried up to 3 times with exponential backoff (1 s / 2 s / 4 s jitter) or the `Retry-After` header value. Shared `HTTP_CLIENT` static (connection pooling via `pool_max_idle_per_host(4)`). **HTTP_CLIENT invariant**: every outgoing HTTP request anywhere in the Rust backend must go through `http_client()` from `api.rs` — never call `reqwest::Client::new()` directly. Creating a new client bypasses connection pooling and drops the `User-Agent` header that modworkshop requires. Both `http_client()` and `user_agent(app)` are `pub(crate)` — import them via `use crate::commands::api::{http_client, user_agent}` when making HTTP requests from outside `api.rs`.

- **`download.rs`** — streams file to `temp_dir()/pd3-mod-{uuid}.{ext}`, emitting `download:progress` Tauri events with `{ downloaded, total }`. `total` is `0` when the server omits `content-length` — callers must handle the indeterminate case.

- **`mods/`** — the most complex module, split into focused subfiles. `mod.rs` holds all `#[tauri::command]` functions and re-exports; the logic lives in:
    - `engine.rs` — `ModEngineConfig` parameterizes all engine behavior per game. Fields: `game_id`, `index_game_name` (matches `games.name` in `index.db` — "PAYDAY 3", "PAYDAY 2", "PAYDAY: The Heist", "Crime Boss: Rockay City"), `state_filename`, `targets: &'static [ScanTarget]`. `ScanTarget` holds `tag: &'static str`, `unit: ModUnit`, `mods_subpath`, `disabled_subpath`, `backup_subpath`. `ModUnit` enum: `File { extension, disabled_suffix, priority_prefix }` for UE pak games (PD3 on UE5, Crime Boss on UE4 — same `.pak`/`~mods` convention); `Directory { entry_markers, scan_markers, index_gated_markers, excluded_names, priority_prefix }` for Diesel/BLT games (PD2, PDTH) and the `ue4ss_mods` target on PD3/Crime Boss. **`entry_markers` vs `scan_markers`**: `entry_markers` drives archive classification during install (`classify_archive_dirs`, `is_unplaceable_pack`); `scan_markers` drives ambient disk scanning (`scan_active`, `scan_disabled` in `paths.rs`) — they are intentionally separate. PDTH mods has `entry_markers: &["mod.txt", "base.lua"]` (so DAHM sub-mod ZIPs install correctly) but `scan_markers: &["mod.txt"]` (so DAHM's ~40 bundled framework modules, which have `base.lua` but no `mod.txt`, are not auto-discovered as untracked mods) — `base.lua` instead sits in `index_gated_markers`, so those folders are _discovered_ but only tracked if their SHA256 matches the mod index. `excluded_names: &'static [&'static str]` is a third, name-based filter for when index-gating can't apply (a bundled folder's content is never hashed into the index at all — see UE4SS below); `scan_active`/`scan_disabled` skip any directory whose name appears there before even checking markers. `engine_for_game(game_id)` dispatches: `"pd2"` → `PD2_ENGINE`, `"pdth"` → `PDTH_ENGINE`, `"cb"` → `CRIMEBOSS_ENGINE`, anything else → `PD3_ENGINE`. Helper fns: `mods_dir`, `disabled_dir`, `backup_dir`, `state_path`. Methods: `primary()` returns `&targets[0]`; `target_for(tag: Option<&str>)` routes by tag, falling back to primary for unknown tags; `disabled_suffix()`, `is_directory_unit()`, `priority_prefix_enabled()` (mirrors `disabled_suffix()`'s match-on-`ModUnit` shape — every site that calls `apply_priority_prefix` must gate on this first, since several targets, e.g. Crime Boss's `mods` and PD2/PDTH's `mods`/`mod_overrides`, manage order via something other than a filename prefix; `reorder.rs`, `folders.rs`, and `state.rs`'s `compact_folder_priorities` all gate on it). Every Tauri command in `mod.rs` starts with `let cfg = engine_for_game(game_id.as_deref().unwrap_or("pd3"))` and passes `cfg` to all lower-level ops. `PD2_ENGINE` has two targets: `mods` (`entry_markers/scan_markers: &["mod.txt", "main.xml"]`) and `mod_overrides` (`entry_markers/scan_markers: &[]` — any directory). `PDTH_ENGINE` has two targets: `mods` (entry/scan markers as above) and `mod_overrides` (`entry_markers/scan_markers: &[]`). `PD3_ENGINE` has two targets: `paks` (primary, `File` unit, `.pak`/`~mods`) and `ue4ss_mods` (secondary, see UE4SS below). `CRIMEBOSS_ENGINE` has three targets, and unlike every other multi-target game its **primary** is the `Directory` one: `mods` (no markers — blanket-accept, same shape as PD2's `mod_overrides`) rooted at `CrimeBoss/Mods`, then `paks` (legacy `File` unit, `.pak`/`~mods`, same convention as PD3) rooted at `CrimeBoss/Content/Paks/~mods`, then `ue4ss_mods` (see UE4SS below). New installs always land in `mods` because `resolve_archive_download` dispatches on `cfg.primary().unit`; `paks` is reachable only via `target_for(Some("paks"))` (ambient scan/enable/disable/uninstall of pre-existing loose-triplet installs, never new installs). See the "Crime Boss" key domain fact below for why.
    - `types.rs` — `InstalledMod`, `ModFolder`, `ModsState`, `InstalledResponse`, `TopLevelItem`. `InstalledMod.location: Option<String>` — scan target tag; `None` = primary target (backward-compatible), `Some(tag)` routes all ops to the named `ScanTarget`. Carries `#[serde(default, skip_serializing_if = "Option::is_none")]` so state files without it still deserialize.
    - `naming.rs` — `strip_priority_prefix` / `apply_priority_prefix` (filenames on disk are always `NNN_name.pak`), `pak_filename`, `hash_filename`, `make_uid`
    - `paths.rs` — `mods_base` / `disabled_base` / `get_state_path` / `active_mod_path` / `disabled_mod_path` / `find_untracked_paks`. `find_untracked_paks` iterates all `cfg.targets`; skips any target whose backup dir exists; builds a per-target known set by stripping the `"<tag>:"` prefix from keys in the caller's `known: HashSet<String>`; returns `Vec<(String, bool, Option<String>)>` — (rel*path, is_enabled, location_tag). Callers must build known keys as `format!("{}:{}", m.location.as_deref().unwrap_or(""), rel_path)`. **Host-pack paths**: `resolve_host_mod_dir` finds an installed host mod's on-disk folder by modworkshop id (from state; active → disabled → conventional name); `host_pack_dir` returns where an installed host pack lives (`<host>/<subpath>/<filename>`); `host_pack_disabled_dir` is the Modrex-managed disabled location \_outside* the host (`mods/disabled/host-<id>/<filename>`).
    - `state.rs` — `read_state`, `save_state` (atomic: writes to `{name}.tmp` then `fs::rename` over the real file — never revert to a direct `fs::write`), `get_folder_path` (recursive, builds slash-separated path from `parentId` chain), `reconcile_state` (marks missing files `missing: true`; migrates legacy `.disabled` paths; migrates `.pd3mm.json` → `.modrex.json` on first run; when backup dir exists: File-unit games read state from inside the backup because the whole folder was renamed; Directory-unit games read from the normal `state_path` because the state file stays in `mods/` and only user mod dirs were moved). `reconcile_state` also: **purges framework-only entries** — on every load, drops entries with no `file_id` and negative `id` that are _either_ missing all of the target's `scan_markers` files on disk (catches DAHM framework modules that were auto-discovered while the `scan_markers`/`entry_markers` split didn't exist yet) _or_ whose filename is on the target's `excluded_names` list (catches UE4SS bundled framework sub-mods collected before `excluded_names` existed — their marker file is still genuinely present, so the first check alone never catches them; Modrex-installed entries with a `file_id` are never touched); removes phantom folders (folders with no mods, no child folders, and no active directory — disabled dir is ignored so a leftover `disabled/` subdir doesn't block cleanup); calls `compact_folder_priorities` to renumber folder disk names to sequential `(1, 2, 3, ...)` within each parent scope (repairs gaps from prior bugs); combines all checks into a single `save_state` call.
    - `zip.rs` — multi-format archive support. `ArchiveFormat` enum (`Zip`, `SevenZip`, `TarGz`, `TarXz`, `Rar`) + `detect_archive` (magic-byte dispatch). Public API: `list_pak_entries`, `extract_entry`, `extract_dir_entry`, `extract_archive_flat`, `classify_archive_dirs`, `is_unplaceable_pack`, `resolve_archive_download`, `mark_archive_files`, `compute_sha256`. **Format dispatch**: all five formats share one enumerator — `list_entries` returns `Vec<ArchiveEntry { name, is_dir }>`, and the listing/classification operations (`list_pak_entries`, `classify_archive_dirs`) are pure functions over it; only extraction stays per-format because unrar can only extract to a directory (it can't expose a per-entry reader). `compute_sha256` streams the file in 64 KB chunks via `spawn_blocking` rather than buffering it whole. **Zip-Slip invariant**: every directory extractor (`extract_dir_*`, `extract_flat_*`) must route its destination through `safe_dest`, which rejects entries with `..`, absolute, or drive/UNC-prefix components; RAR extraction additionally validates entry names before `extract_with_base` (which writes by internal name). `resolve_archive_download` returns `ResolvedArchive` (a type alias for `Result<(PathBuf, Option<PathBuf>, Option<String>), String>`) — the third element is `location_tag` (`None` for primary, `Some(tag)` for secondary). For Directory targets it runs `classify_archive_dirs(names, cfg)`, which tags every mod dir with its destination: marker dirs (`mod.txt`/`main.xml`, at any depth via `rfind`) → their target; marker-less dirs at the **same depth** as marker dirs (or every top-level dir when the archive has no markers) → the override target; an explicit `assets/mod_overrides/<name>/` segment unwraps to the dir _inside_ it (handles packs double-wrapped in the game path). A single dir resolves directly; multiple dirs emit `ZIP_MULTI_PAK` with a single top-level `targetTag` when all entries share one target, or a parallel `entryTags` array when the archive spans targets (a mixed modpack) so the picker routes each entry independently. Two guards run before classification (PD2 only): `detect_host_pack` (see `host_mods.rs`) returns a `HOST_MOD_PACK` sentinel for content packs that install _inside another mod_, and `is_unplaceable_pack` returns `UNRECOGNIZED_ARCHIVE` for a flat folder of loose files (no marker, no nested asset structure) that can't be placed in any scan target. **UE4SS routing** (both `resolve_archive_download`'s File-unit branch and `resolve_crimeboss_archive`): when an archive has zero `.pak` entries, before erroring it first checks `has_ue4ss_loader_signature` (a top-level `UE4SS-settings.ini` — the one marker that's only ever present in the _full_ loader package, never a standalone sub-mod, since the bundled framework sub-mods ship alongside it with the exact same `Scripts/main.lua` shape a real sub-mod has) and emits an internal `UE4SS_LOADER:<zipPath>` sentinel (handled entirely in `mod.rs`, never reaches the renderer); if that's absent, `try_classify_as_directory_target` falls back to `classify_archive_dirs` against `cfg.targets` (which already includes `ue4ss_mods` for PD3/Crime Boss even though it's never primary) to catch a standalone Lua sub-mod archive. Each format has private helpers (`_zip`, `_7z`, `_tar<R>`, `_rar`). **sevenz-rust callback invariant**: the `bool` returned by the `decompress_with_extract_fn` closure controls iteration — `Ok(false)` stops, `Ok(true)` continues. Non-matching entries must drain their bytes via `std::io::sink()` before returning `Ok(true)` to stay stream-aligned in solid 7z archives. **unrar extraction pattern**: `open_for_processing()` uses a typestate loop — `archive.read_header()` moves `archive` into the returned `Header`; `header.skip()` and `header.extract_with_base(dir)` move it back. RAR extraction writes to a temp dir (the unrar API can only extract to a directory, not a single file path) then copies to `dest`; cleanup is guaranteed via an IIFE closure. `mark_archive_files` returns `(Vec<InstalledMod>, bool)` — the bool is `true` when at least one mod was newly checked (dirty flag for the caller to persist state). Skips mods where `archive_broken.is_some()` so repeated calls are O(1). `InstalledMod.archive_broken: Option<bool>`: `None` = unchecked, `Some(false)` = clean, `Some(true)` = broken; persisted in the state file so magic-byte scanning is amortized across launches.
    - `install.rs` — `install_mod_from_path`, `uninstall_mod_op`, `enable_mod_op`, `disable_mod_op`. All accept `cfg: &ModEngineConfig` and a `target: &ScanTarget` (derived via `cfg.target_for(m.location.as_deref())`). `install_mod_from_path` sets `location: None` for the primary target, `Some(target.tag)` for secondary (uses `std::ptr::eq(target, cfg.primary())`). File ops use extension rename / file copy / remove*file; Directory ops use dir move / recursive copy / remove_dir_all. Priority prefix applied only when `target.unit.priority_prefix` is true. `enable_mod_op`/`disable_mod_op` special-case `target.tag == "ue4ss_mods"`: call `ue4ss_modstxt::sync_enabled` and flip the tracked flag, then `return` *before* the file-move block runs — see UE4SS below for why moving the folder would do nothing. `launch_game` and `launch_without_mods` both call `maybe_suppress_crash_reporter` before spawning, so any future cleanup-only setting should stay launcher-gated and best-effort. `uninstall_mod_op` removes only the selected mod files and leaves now-empty app folders in state/on disk; folder removal is explicit via `delete_folder_op` or reconciliation of phantom folders whose active directory is gone. **Host packs** (`location` starting `host:` — see `host_mods.rs`) take dedicated branches in every op: `install_host_pack_op` extracts a set into the host mod's folder and records it; `uninstall_mod_op` removes from the active \_or* disabled location; `enable_mod_op`/`disable_mod_op` call `move_host_pack`, which moves the set between the host's subfolder and `mods/disabled/host-<id>/` (flipping only the `enabled` flag would leave the set loading in-game).
    - `host_mods.rs` — declarative registry of **host mods**: mods whose add-on content packs install _inside another mod's folder_ rather than at a scan-target root (the canonical case is Menu Backgrounds, modworkshop `17160` → `Assets/`). `HOST_TARGETS` carries `host_mod_id`, `host_name`, `subpath`, a filename `signature` + `min_matches`, and `bundled` (set names the host ships itself, e.g. Menu Backgrounds' `"The Diamond"`). `detect_host_pack(names)` recognizes a pack by content signature (rejecting anything with a `mod.txt`/`main.xml` marker). A recorded pack's `InstalledMod.location` is `host:<id>:<subpath>`; `parse_host_location` / `host_target_by_id` read it back. The host's on-disk folder is always resolved from installed state by id, never assumed from its name. **Recovery after a state rebuild**: host packs live inside another mod, so the scan-target walk can't find them — `find_untracked_host_packs` (in `paths.rs`) scans the host's `subpath` (and the disabled area) for untracked set folders, excluding `bundled` defaults. `get_installed` then identifies each by its representative file's SHA256 against the index (`hashable_file_for_mod_dir` + `lookup_sha256`): a hit restores the real id/name/version, a miss leaves a negative-id, folder-named entry whose stored sha256 lets a later index update upgrade it. **Modrex installs and tracks the files only — it never writes a host mod's own runtime/in-game settings to "activate" a pack** (e.g. Menu Backgrounds' `BGsSet` option is the user's to set in-game). Note: a host pack is only index-identifiable if its source mod is in `index.db` — e.g. a large RAR was unindexed until the `modrex-index` RAR/7z size cap was raised (a backfill run picks up the backlog).
    - `reorder.rs` — `reorder_mods_in_folder_op`, `move_mod_to_folder_op`, `reorder_children_op`
    - `folders.rs` — `create_folder_op` (idempotent: reuses an existing folder with the same `display_name` under the same `parent_id` instead of creating a duplicate record — callers that create folders in a loop, e.g. `ZipPickerModal`'s auto-folder-creation, can safely call it repeatedly for the same path without producing two state records that collide on one on-disk directory), `move_folder_op`, `rename_folder_op`, `delete_folder_op`
    - Key invariants:
        - `disabled_mod_path` appends `.disabled` to the `.pak` filename for File mods — the extension change is what disables mods (UE5 scans all subdirectories of `Paks/`, so subdirectory alone is insufficient). For Directory mods, disabling moves the folder into `disabled/`.
        - `get_installed` accepts `game_id: Option<String>` and uses `engine_for_game` to select the correct engine. All games are handled; there is no pd3-only guard.
        - `get_installed` identification pipeline: (1) SHA256-then-name index lookup upgrades negative-id entries; (2) name-suffix pass re-assigns positive ids; (3) untracked mods are auto-folder-created, reconciled by SHA256, then identified by hash → embedded modworkshop id → name (precedence detailed below). New untracked entries use `by_uid.entry().or_insert(...)` — existing entries are never overwritten. The command body is a thin orchestrator; each stage lives in a named helper: `upgrade_negative_ids`, `regroup_negative_ids_by_name_suffix`, `ensure_untracked_folders`, `hash_untracked`, and `identify_untracked` (Phase 1 SHA256 reconcile + Phase 2 identify, sharing one `sha256_to_uid` map). **Phase 2 precedence per mod**: exact SHA256 hit → **embedded modworkshop id** (Directory-unit/BeardLib mods only — `embedded_modworkshop_id` parses `<AssetUpdates provider="modworkshop" id="N">` from the mod's `main.xml`, enriched via `mod_index::query_mod_by_id`; preferred over the fuzzy name match because the embedded id survives version drift) → **name fallback** (`query_by_name` → numeric-stripped filename → `hash_filename`). An embedded-id mod's installed version is its own `main.xml` declaration, falling back to the index's current version so a drifted-old install reads as outdated rather than nagging a false "unknown" update. `upgrade_negative_ids` (renamed from `upgrade_negative_ids_by_sha`) tries SHA256 first, then falls back to `lookup_by_name(m.name)` on every miss — not just at first discovery. This matters because SHA256 misses permanently once a mod's modworkshop file is updated after install (the old installed bytes can never match a newer hash again); without the name retry, a mod that missed both checks once (e.g. because the local index happened to be stale at that exact moment) would stay "Unknown" forever, since this was previously the _only_ re-identification pass that runs on every refresh — the user would have had to wipe `.modrex.json` to force a fresh `identify_untracked` pass. Returns `bool` — both early-return paths (`mods_hidden` and `untracked.is_empty()`) check it and call `save_state` when true, so recovered positive IDs are never lost on the next write.
        - `install_mod` stores the **mod-level** version from `/mods/{id}` (not the file-level version from `/files/latest`). It inherits `folder_id` from existing state when the caller omits it.
        - **Multi-file installs**: `install_mod_from_path` finds `existing` by `uid` only (not `id`). `install_mod` pre-removes the old pak when exactly one same-id entry exists — never do this inside `install_mod_from_path`.
        - **ZIP installs**: `install_from_zip_entry` uid is `{file_id}_{entry_stem}`; SHA256 match reuses existing uid so reinstall moves in-place. `folder_id` is always caller-provided (never inherited from existing entries). `location_tag: Option<String>` param routes the install to the correct `ScanTarget`. Mirrors `install_mod`'s pre-removal: when the resolved uid doesn't match any existing entry and exactly one other entry shares this mod id, that entry is uninstalled first — without this, a mod whose file packaging changes between a bare `.pak` (uid = `file_id`) and an archive (uid = `{file_id}_{entry_stem}`) leaves the old uid orphaned as a second tracked entry for the same mod, which also suppresses the update prompt (the dedup-by-id check in `useModData`'s `updatable` sees the new version already installed under the other uid).
        - `InstalledMod.uid` has `#[serde(default)]` so state files predating the uid field still deserialize
        - **Multi-target routing**: `cfg.target_for(m.location.as_deref())` is the canonical way to get a mod's `ScanTarget` in any op. Folder ops (`create_folder_op`, `move_folder_op`, etc.) always use `cfg.primary()` — app folders live only in the primary target's directory tree.

- **`launchers/`** — split into focused files so touching one launcher never requires touching another:
    - `types.rs` — `GameDef` struct (`name`, `executable`, `process_name`, `steam?`, `epic?`, `xbox?`) and `Launcher` trait (`id`, `is_installed`, `find_game`, `identify_path`, `launch`)
    - `games/pd3.rs`, `games/pd2.rs` — one file per game; add new games as `games/<name>.rs`
    - `steam.rs` — Windows: `reg query` for install path, then walks `libraryfolders.vdf`; Linux: checks `STEAM_DIR`, `XDG_DATA_HOME`, snap, flatpak paths. `find_game` requires `game.executable` to exist inside the candidate folder — a leftover folder without the exe is not counted as installed. The Windows `reg query` result is cached in a `OnceLock<Option<String>>` for the process lifetime — never call `reg query` for Steam's install path outside this helper. The query runs through `run_bounded` (5 s).
    - `epic.rs` — reads `%PROGRAMDATA%\Epic\...\Manifests\*.item` JSON
    - `xbox.rs` — `find_in_drives` scans every subdirectory of each mounted drive root for `{dir}/{game.name}/Content/` containing the xbox executable; falls back to `find_via_package_manager` (PowerShell `Get-AppxPackage`, via `run_bounded` with a 15 s cap) for deeply nested installs; launches via `gamelaunchhelper.exe`. Xbox game path always ends in `/Content`. **`fixed_drive_roots` gate** (raw `GetLogicalDrives` + `GetDriveTypeW` externs — no windows crate dep; neither call does volume or network I/O): drives come from the live mount bitmask (A–Z, never a hardcoded letter list — a game drive on `H:` is a real setup) and only `DRIVE_FIXED` volumes are scanned, because the per-subdirectory stats block for the SMB redirector timeout on disconnected network/VPN drives and can stall on empty card readers — the cause of a real "Modrex is not responding" startup freeze — and Xbox installs only ever live on fixed NTFS volumes.
    - `mod.rs` — orchestration (`identify_launcher_for_path`, `launch_with`, `all_launchers`) + all Tauri commands. `game_def_for_id(game_id: &str) -> &'static GameDef` maps `"pd2"` to `&PD2`, `"pdth"` to `&PDTH`, anything else to `&PD3`. Marker files for `identify_launcher_for_path`: `steam_appid.txt`, `.egstore/`, `MicrosoftGame.config`. `configure_game_path(None)` validates the existing saved path first (checks `game.executable` exists there) and preserves the saved launcher as-is — it does not re-run `identify_launcher_for_path` on valid paths, because doing so clobbers games without marker files. Only re-detects launcher+path if the path is stale or absent. `findGamePath()` in `api.ts` always calls `configure_game_path(null)` on every refresh — this is how stale paths (game uninstalled but folder left behind) get cleared. `is_game_running`, `launch_game`, `launch_without_mods`, `restore_mods`, `stop_game` all accept `game_id: Option<String>` and dispatch via `game_def_for_id` / `engine_for_game` — fully multi-game. The renderer passes `activeGame` to all five. The `-fileopenlog` warning in `TopBar` remains PD3-only (guarded by `activeGame === 'pd3'`). Private `do_restore(game_path, cfg)` is the shared restore implementation called by both `launch_game` (best-effort, errors ignored) and `restore_mods` (errors returned). `launch_game` calls it first so mods left in backup from a prior "launch without mods" session are restored before the game starts. Both `do_restore` and `launch_without_mods` iterate `cfg.targets` — each target gets its own backup dir; `base/` exclusion applies only to the primary target (index 0).
    - **Main-thread invariant**: sync Tauri commands run on the main thread, so a blocked probe freezes the window ("Modrex is not responding"). `auto_detect_game`, `installed_launchers`, `configure_game_path`, and `is_game_running` are therefore `async` and run their work via `tauri::async_runtime::spawn_blocking` — never convert them back to sync, and route any new detection command through the same pattern. Detection subprocesses (`reg query`, `Get-AppxPackage`) go through `run_bounded` (in `mod.rs`), which polls with a deadline and kills the child instead of `.output()`'s unbounded wait — the same lesson as the old tasklist/WMI freeze fix, now applied to every probe. `run_bounded` sets `CREATE_NO_WINDOW` and pipes stdout itself; it reads stdout only after exit, so it's only suitable for small-output commands (single-line results). Both `detect_game` and `installed_launchers` gate each store on `is_installed()` before probing and log `probing <launcher> for <game>` before each `find_game` — the last such line in `Modrex.log` pinpoints a hung probe, which is otherwise traceless.
    - **Windows `CREATE_NO_WINDOW` invariant**: The release binary sets `windows_subsystem = "windows"` (`main.rs:1`), so it has no console. Any `std::process::Command` on Windows without `creation_flags(0x08000000)` spawns a visible console window. In debug builds (`pnpm dev`) this is invisible because the process inherits the parent console. Every spawn of a **console-mode executable** (cmd, tasklist, PowerShell, cargo, pkill, pgrep) must use `use std::os::windows::process::CommandExt` and `.creation_flags(0x08000000)`. GUI shell programs (`explorer.exe`, `xdg-open`) are exempt — they never attach to a console regardless.

- **`superblt.rs`** — SuperBLT loader (PD2 only) detect + install. `check_superblt` reports the loader present if any of `WSOCK32.dll` (current) / `IPHLPAPI.dll` (legacy) / `libsuperblt_loader.so` (Linux native) sits in the game **root** — the loader never lives under `mods/`, so its root presence is the only reliable install signal. `install_superblt` downloads the loader zip from `sblt-update.znix.xyz` and extracts `WSOCK32.dll` into the game root; the BLT basemod (`mods/base`) is fetched by the loader itself on next launch, not by Modrex.

- **`pdth_overrides.rs`** — PDTHModOverrides loader (PDTH only) detect + install. Checks for both `DINPUT8.dll` and `PDTHModOverrides.dll` in the game root. `install_pdth_overrides` downloads and extracts the release ZIP into the game root. Treated as a loader mod (modworkshop id 53474) — the UI shows "Installed" via DLL presence, not state tracking. Commands: `check_pdth_overrides`, `install_pdth_overrides`.

- **`dahm.rs`** — DAHM hook framework (PDTH only) detect + install. Checks for `lightfx.dll` in the game root. `install_dahm` downloads from `LOADER_DOWNLOAD_URL = "https://dahm.neonsynth.de/main.php"` and extracts the full ZIP to the game root via `extract_zip_to_dir` (includes inlined zip-slip guard `safe_dest`). DAHM ships ~40 framework modules into `mods/` using `base.lua` (no `mod.txt`) — this is why `entry_markers` and `scan_markers` are split on PDTH's mods target. DAHM sub-mods (installed by the user via Modrex) are regular mods tracked in state; DAHM's own framework modules are never tracked. Treated as a loader mod (modworkshop id 14267) — UI shows "Installed" via `lightfx.dll` presence. Commands: `check_dahm`, `install_dahm`.

- **`ue4ss.rs`** — UE4SS loader (Lua scripting/native modding framework) detect + install, for both Crime Boss and PD3 (unlike SuperBLT/DAHM/PDTHModOverrides, which are each single-game). Same shape as those — `is_installed`/`check_ue4ss` present-detected, `install_loader` one-shot extraction, never tracked in `state.json` or uninstallable through Modrex — but `Ue4ssDescriptor` (`proxy_dlls: &'static [&'static str]`, `binaries_subpath`) is parameterized per `(game_id, launcher)` rather than hardcoded, because UE4SS for PD3 has **multiple independently-maintained mod pages distributing it over time, each with a different proxy DLL**: the older "PD3 UE4SS / Allow Pak Mods" (modworkshop id `44048`, Narknon) uses `dxgi.dll`; the newer "PD3 UE4SS V3.01 + Allow Pak Mods" (id `47771`, Shalashaska) uses `xinput1_3.dll` — both verified against their real downloaded archives, and `is_installed` checks every known name so it doesn't matter which release a user actually has. Crime Boss ("UE4SS-CB", id `47749`) has a single maintainer and a single proxy (`dwmapi.dll`) — no equivalent variance there, at least so far. Only Steam (Crime Boss) and Steam/Epic (PD3) are verified; Xbox/GamePass is unsupported rather than guessed (different destination, unverified proxy). There is **no dedicated install command and no canonical download URL** — unlike SuperBLT/DAHM, each release is just a regular modworkshop mod page with no guaranteed long-term host, so installing it goes through the _normal_ mod-install flow; `zip.rs`'s `UE4SS_LOADER` sentinel (see above) is what routes a normal `install_mod`/`install_file` call here instead of erroring on "no .pak files inside". `install_loader` extracts the whole downloaded archive flat into the resolved `Binaries/<platform>` dir via `extract_archive_flat` — content-driven, so it doesn't matter which proxy DLL the specific download happens to contain. The `Mods/` folder UE4SS creates holds both bundled framework sub-mods and (if installed) real user sub-mods — see the `ue4ss_mods` `ScanTarget` and `excluded_names` above, and `ue4ss_modstxt.rs` below. Commands: `check_ue4ss` only (`install_loader` is `pub(crate)`, called from `mod.rs`'s `install_mod`/`install_file`, not its own Tauri command).

- **`mods/ue4ss_modstxt.rs`** — syncs a UE4SS Lua sub-mod's enabled state into `Mods/mods.txt`, the file UE4SS itself reads on launch to decide what loads — moving the sub-mod's folder has no effect, mirroring `crimeboss_settings.rs`'s "enable/disable doesn't work by moving files" lesson in a different shape. Real format (verified against both the Crime Boss and PD3 releases): `ModName : 1`/`: 0` lines, `;`-comments, blank lines, a leading UTF-8 BOM — which Rust's string handling does **not** strip automatically, so the very first entry in the file needs explicit BOM-stripping (`entry_name`) or it never matches by name. `set_enabled_in_mods_txt` rewrites only the matched line in place (preserving everything else byte-for-byte) or appends a new one if the mod has no entry yet — never invents a file from scratch (no-ops if `mods.txt` doesn't exist, same tolerance as `crimeboss_settings`). Unlike Crime Boss's ModSettings, there's no resolution chain needed (no external "Saved Games" indirection — the file sits right inside the already-known `Mods/` dir), so `sync_enabled`/`read_enabled` take the path directly rather than a `mod_path` + launcher. `read_enabled`/`read_enabled_from_mods_txt` exist and are tested but **not wired into any resync path** — Crime Boss needs one because the game has an in-game Options > Mods toggle that can disagree with Modrex's tracked state; UE4SS has no known equivalent, so this is a deliberate scope decision, not an oversight, unless evidence of an external toggle surfaces.

- **`updater.rs`** — auto-update flow via `tauri-plugin-updater`. `UpdaterState` (managed Tauri state) holds the pending `Update` object and its downloaded bytes across two separate commands. Three-phase sequence: `check_for_update` fetches metadata and stores the `Update` object, emitting `updater:update-available`; `download_update` streams bytes and emits `updater:update-progress` (percent) then `updater:update-ready`; `install_update` takes both and applies. Strategy is always `"manual"` — there is no auto-install path.

- **`thumbnails.rs`** — Thumbnail disk cache. `get_thumbnail(filename)` checks `app_cache_dir()/thumbnails/thumbnail_{filename}`, downloads from `https://storage.modworkshop.net/mods/images` if absent (6-slot semaphore, atomic write via `.tmp` rename), and returns the **cache filename** (not a path) for the renderer to build its `thumb://` URL. By default it downloads the pre-generated `thumbnail_{file}` CDN variant, falling back to the original for old images with `has_thumb: false`; with `full: true` it caches the original under `{filename}`. **Variant policy**: the small variant is only **256 px wide** and upscales badly — use it solely for renders ≤ ~120 px (`ModListRow`'s `w-28` thumb, `DependencyRow`'s 40 px icon); everything wider (`ModCard`, gallery tiles, banner, lightbox) must use `full: true`. The CDN sends no cache headers, so direct CDN URLs cost a download or revalidation round-trip per view — always go through this cache. `cleanup_thumbnail_cache` runs fire-and-forget at startup and removes files whose `modified()` time exceeds 90 days. The modworkshop CDN sends no `Cache-Control` header (`cf-cache-status: DYNAMIC`), so without this every app launch revalidates images over the network. `handle_thumb_protocol` backs the custom `thumb://` URI scheme (registered in `lib.rs`): it serves files from the thumbnails cache dir with `Cache-Control: public, max-age=31536000, immutable`. `sanitize_thumb_filename` percent-decodes the URI path and rejects separators/`..` — every request must pass it before touching the filesystem (path-traversal guard; unit-tested).

- **`mod_index.rs`** — SHA256-based mod identification. Downloads `index.db` from the `modrexio/modrex-index` GitHub release to `app_data_dir()`, cached with a 1-hour TTL (fire-and-forget at startup). `query_sha256(conn, sha256, game_name)`, `query_by_name(conn, name, game_name)`, and `query_mod_by_id(conn, mod_remote_id, game_name)` (newest indexed file for a known modworkshop id — used to enrich embedded-id matches) are private helpers that take a `&rusqlite::Connection` — testable with in-memory SQLite. Both join `files → mods → sources → games` and filter by `games.name = game_name` so a PD2 hash never matches a PD3 mod. `lookup_sha256` / `lookup_by_name` are the public wrappers (accept `&AppHandle` and `game_name`); callers pass `cfg.index_game_name`. `lookup_by_name` returns `Some` only when exactly one mod matches (ambiguous = `None`) — used both by `identify_untracked`'s name fallback and by `upgrade_negative_ids`'s every-refresh retry (see above). Uses `rusqlite` with `features = ["bundled"]` — no native module issues.

- **`news.rs`** — scrapes `paydaythegame.com`'s per-game news category page (`category_slug`: `"pd2"` → `payday2`, `"pdth"` → `theheist`, else `payday3`) for the News tab. **Fetches via a `curl` subprocess, not `reqwest`**: the site's Cloudflare bot management 403s every library HTTP client tried (`reqwest`, .NET `HttpClient`) regardless of headers — a TLS/HTTP2 fingerprint check — and a renderer-side `fetch()` is blocked too since the site sends no `Access-Control-Allow-Origin` header; `curl.exe` is the one client that passes (verified live), so `curl_fetch` shells out to it with `creation_flags(0x08000000)` on Windows, matching the `reg query`/`powershell` subprocess pattern in `launchers/`. `parse_news_html` (pure, HTML-in/`Vec<NewsItem>`-out) and `extract_total_pages` (parses the WP-PageNavi block — the total is the max page number across every `.wp-pagenavi a` link plus the `.current` span, since WP-PageNavi omits the link to whichever page you're already on) are both unit-tested against saved fixtures. `fetch_news`/`refresh_news` (page 1 only) are TTL-cached to `app_data_dir()/news-{slug}.json` (1 hour, same atomic `.tmp`-then-rename write as `mod_index.rs`); `fetch_news_page(game_id, page)` fetches any other page uncached. All three return `NewsResult { items, total_pages }`.

- **`analytics.rs`** — anonymous, opt-in GA4 usage telemetry via the Measurement Protocol, sent from Rust. See the **Usage analytics** section below for the full design.
