### Renderer (`src/renderer/src/`)

**`api.ts`** — the only place `invoke` / `listen` are called. All other renderer code imports from here. `onEvent<T>` wraps `listen` with a cancellation-safe pattern (resolves the `UnlistenFn` async, cancels immediately if component unmounts first). `getGameSettings(gameId)`, `setGamePath(path, gameId?)`, `setLauncher(launcher, gameId?)`, `setLaunchOptions(opts, gameId?)`, `getInstalledLaunchers(gameId?)` all accept an optional `gameId` that defaults to `"pd3"` on the Rust side. `getInstalled(gameId?)` also accepts an optional `gameId` — always pass `activeGame`. All mod operation functions (`installMod`, `uninstallMod`, `enableMod`, `disableMod`, `reorderModsInFolder`, `moveModToFolder`, `reorderChildren`, `moveFolder`, `createFolder`, `renameFolder`, `deleteFolder`, `openModsFolder`, `installFromZipEntry`, `installModFile`) accept a trailing `gameId?: string` parameter — always pass `activeGame` from context. Rust defaults to `"pd3"` when `gameId` is `undefined`/absent. `installFromZipEntry` also accepts a trailing `locationTag?: string` parameter forwarded to Rust — pass `payload.targetTag` from `ZipMultiPakPayload`.

**`App.tsx`** — owns `installed`, `gamePath`, `modsHidden`, `activeGame` as sources of truth. `detailStack` is `{ modId: number; initialMod?: Mod }[]` — each entry carries the optional browse-list `Mod` object so `ModDetailPage` can render the header instantly before the full fetch completes. `openDetail(modId, from, initialMod?)` resets the stack to a single entry; `pushDetail(modId)` appends (or truncates to an existing entry) without an `initialMod`. `View` type includes `'welcome'` in addition to the nav views. `getInitialView()` returns `'welcome'` when `modrex:active-game` is absent from localStorage (first launch). `activeGame` initializer reads localStorage and accepts any valid `GameId` (`pd2`, `pdth`, `cb`, `raid`, `pd3`; the valid-id list is hardcoded there — a new game must be added to it) — never assume it defaults to `pd3`. `handleGameChange(g)` restores `gamePath` from `gamePathCache` and `installed`/`folders`/`modsHidden` from `installedCache` (so the UI never flashes "game not found" or "no mods installed" while re-validation runs in the background), saves the game to localStorage, and navigates to the saved nav view — all state updates wrapped in `startTransition`, because the switch commit renders three pages' worth of tree at once and a transition keeps it interruptible (rapid switching cancels the in-progress render instead of queueing jank). Falls back to empty state when a game has never been loaded this session. Installed readiness is per-game: `readyGames: ReadonlySet<GameId>` holds the games whose installed list has been fetched at least once this session. The startup splash shows while the set is empty; `InstalledPage` receives `installedReady={readyGames.has(activeGame)}` so the first fetch for each game shows "Loading…" instead of a false "No mods installed yet". `handleShowWelcome()` navigates back to the welcome screen. When `view === 'welcome'` the entire TopBar/Sidebar is hidden — only `WelcomeScreen` renders inside the root div. App version shown in `TopBar.tsx` comes from `import.meta.env.VITE_APP_VERSION`, injected by Vite's `define` in `vite.config.ts` from `package.json` at build time; shows `v-dev` in dev mode. `TopBar` receives `activeGame: GameId` — the `-fileopenlog` launch-option warning is PD3-only and is suppressed for other games; `SettingsPage` likewise hides the `-fileopenlog` description and placeholder for non-PD3 games. Only PD3 requires `-fileopenlog`; PD2 and PDTH do not. On startup, on every window focus (500ms debounce), and after a manual path change (`SettingsPage`'s `onGamePathChange`), `refreshAll` runs — it awaits `refreshGamePath` before `refreshInstalled`, because `get_installed` reads the game path from settings and a concurrent fetch can return a false-empty list before path detection has persisted. All nav pages (and detail-stack entries) stay mounted as `absolute inset-0` panes inside the `relative` `<main>`, toggled with `invisible pointer-events-none` — **never `hidden`/`display:none`**: un-hiding a `display:none` subtree re-layouts it from scratch and re-decodes every image, which made tab switches stutter; a visibility flip is paint-only and preserves layout, decoded images, and scroll. `BrowsePage` is wrapped in `memo` with stable callbacks (`openDetailFromBrowse`, `goToSettings`) so hidden re-renders are skipped, and receives `isActive={view === 'browse'}`: its fetch effect no-ops while inactive and re-runs the SWR check (`browseCache.ts`: show cached, background re-fetch if stale) on activation; scroll resets only on filter changes, so position survives tab switches. It still remounts on game change via `key={activeGame}`. Inside `BrowsePage`, the card grid is a `memo` boundary (`ModGrid` → per-card `GridCard`): the grid re-renders only when its data props change — never on `isActive` flips, search keystrokes, or modal/error state — and a grid re-render (e.g. download progress) re-renders only the affected card. All handler props crossing that boundary must stay `useCallback`-stable or the memo is defeated. `refreshInstalled` short-circuits (no state updates) when the fetched result deep-equals the `installedCache` entry — focus refreshes usually change nothing, and the fresh array refs would otherwise re-render the installed list and browse grid on every refocus. `SettingsPage` uses `key={activeGame}` to force a full remount on game change, ensuring stale per-game state (launcher, paths) never bleeds through.

**`activeGameRef`** — a `useRef<GameId>` kept in sync with `activeGame` via `useLayoutEffect`. Used by `refreshGamePath` and `refreshInstalled` to discard results that arrived after a game switch. **Must be updated via `useLayoutEffect`, never during the render body** — the `react-hooks/refs` ESLint rule enforces this; writing to a ref in the render body is an error caught by the pre-commit hook.

**`isRefreshingInstalled`** — a `useRef<boolean>` declared alongside `activeGameRef` and reset to `false` in the same `useLayoutEffect` on game switch. `refreshInstalled` checks it at entry and returns early if `true`, then sets it `true` for the duration of the Tauri call and clears it in `finally`. Prevents two concurrent `get_installed` invocations (focus debounce + manual refresh) from racing `save_state` and overwriting positive IDs with negatives.

**`gamePathCache`** — a `useRef<Partial<Record<GameId, string | null>>>({})` that stores the last resolved path for each game per session. `refreshGamePath` writes to it after every successful `findGamePath` call. `handleGameChange` reads from it to restore the previous path immediately, preventing the "game not found" flash while the background re-validation completes. `undefined` means the game was never resolved this session; `null` means it was resolved but not found.

**Failed-detection throttle** — `failedDetectAt` (a ref in `App.tsx`) records when detection returned "not found" per game; `refreshGamePath` skips re-detection for `DETECT_RETRY_MS` (5 min) after a failure, because re-detecting a missing game runs the full launcher scan on every switch/focus otherwise. `SettingsPage`'s `onGamePathChange` is wired to `handleGamePathSet`, which clears the marker before refreshing — a manual path pick must bypass the throttle.

**`gamePathReady`** — a boolean state in `App.tsx` that is `false` while the active game's path is still being resolved this session (auto-detection can take seconds — Steam VDF walk, Epic manifests, Xbox drive scan). Set `true` by `refreshGamePath` on completion; `handleGameChange` sets it from `gamePathCache` presence (`cachedPath !== undefined`). Passed to `BrowsePage` and `SettingsPage`, which must never render a definitive negative ("Game not found" banner, red "could not detect" text) until it is `true` — while `false`, `BrowsePage` renders nothing and `SettingsPage` shows a neutral "Detecting…" placeholder. Components that only disable actions on a falsy `gamePath` (`TopBar`, install buttons) don't need it.

**`installedCache`** — a `useRef<Partial<Record<GameId, { mods, folders, modsHidden }>>>({})` that mirrors `gamePathCache` for installed mod state. `refreshInstalled` writes to it after every successful fetch. `handleGameChange` reads from it to restore the previous installed list immediately, preventing the "no mods installed yet" flash on the Installed page while the background re-validation completes. `undefined` entry means the game was never loaded this session — falls back to the empty reset.

**`WelcomeScreen.tsx`** — full-screen game picker shown on first launch and when the user clicks the game switcher in the sidebar. Banner images load from Steam CDN (`cdn.akamai.steamstatic.com/steam/apps/{appid}/library_600x900.jpg`) with a per-game gradient fallback on `onError`. Selecting a game calls `onSelectGame(g: GameId)` which is wired to `handleGameChange` in `App.tsx`.

**`Sidebar.tsx`** — game switcher is an `ArrowLeftRight` + full game name button at the top; clicking calls `onShowWelcome`. No game-selection logic lives in the sidebar itself. A "Documentation" button (`CircleHelp` icon) sits above the collapse button and calls `api.openExternal` to open `https://modrex.net/docs/` in the system browser.

**`modCache.ts`** — 5-minute in-memory TTL cache for mods, files, and links; all three are persisted to localStorage (24-hour shelf life) under `modrex:mod-cache`, `modrex:files-cache`, `modrex:links-cache`. On module init, `loadFromStorage()` pre-warms all three Maps from localStorage. Writes are debounced 2 s via `scheduleStorage()` which flushes all three keys in one pass. Always use `getCachedMod` / `getCachedModFiles` / `getCachedModLinks` — never call `api.getMod`, `api.listModFiles`, or `api.listModLinks` directly. Three synchronous accessors return cached entries without fetching: `getModCacheEntry(id)` returns `{ mod, fetchedAt }`; `getFilesCacheEntry(id)` returns `{ files, fetchedAt }`; `getLinksCacheEntry(id)` returns `{ links, fetchedAt }`. These are used by `ModDetailPage` to sync-initialize state on mount, bypassing the loading spinner when data is already warm.

**A fourth, deliberately separate cache** — `installedMetaCache` (`INSTALLED_META_TTL_MS`, 30 min, exported so `useModData`'s own staleness check stays in lockstep; persisted under `modrex:installed-meta-cache` alongside the other three) — backs `fetchInstalledModsMeta(workshopId, ids)`, which bulk-refreshes installed-mod metadata via the `ids[]` listing filter (chunked ~50 ids per call, see `api.rs`) instead of one `get_mod` per id. **Invariant: entries here must never reach `modCache`.** The `ids[]` filter returns the list-item shape — missing `images`/`dependencies`/`changelog`/full `banner` — and `ModDetailPage` seeds from `getModCacheEntry` treating any hit as complete (skips re-fetching for the TTL window), so a thin entry leaking into `modCache` would silently render a broken detail page (no gallery, no dependency warnings) until the cache expired. `fetchInstalledModsMeta` unconditionally fetches and caches whatever ids it's given — the caller (`useModData`) decides what's stale, mirroring the per-id functions' division of labor above. Ids missing from the response (deleted mods) come back in `failedIds`. Each chunk awaits `waitForForegroundClear()` (`requestPriority.ts`) first, so this silent bulk refresh yields to whatever the user is actively waiting on. `getInstalledMetaEntry(id)` is the sync accessor, used the same way as the three above.

**`requestPriority.ts`** — lets background API work defer to foreground work so it doesn't sit queued behind silent background calls on the shared rate-limited connection to modworkshop. `markForegroundActivity()` (called by `BrowsePage.fetchMods` and `ModDetailPage.fetchData`, at both start and completion) and `waitForForegroundClear()` (awaited by `modCache.ts`'s `fetchInstalledModsMeta` before each chunk, and by `BrowsePage`'s hover-prefetch before firing) track **recency of foreground activity** — a single `lastForegroundAt` timestamp — rather than an in-flight counter, deliberately: a call site that forgets to mark completion can't permanently starve background work, since at worst `waitForForegroundClear` just waits out one 1.5 s quiet window and proceeds anyway. The "never marked" sentinel is `-Infinity`, not `0` — `0` collided with tests that fake the clock to epoch 0, reading as "foreground just active" and hanging forever on a timer that never advances (caught by `requestPriority.test.ts`).

**`BrowsePage.tsx`** — `fetchMods` calls `markForegroundActivity()` around the `api.listMods` call (start and `finally`) so the installed-mod bulk refresh and hover-prefetch yield to it. `handlePrefetch` (the 150 ms hover-debounced `getCachedMod`/`getCachedModFiles`/`getCachedModLinks` prefetch) awaits `waitForForegroundClear()` before firing. On a fetch failure, `isRateLimitError(error)` matches the literal `"API 429"` substring `api.rs`'s `api_get` produces (not just `"429"`, so a mod id containing 429 inside some other error's path never false-positives) and selects a friendly amber notice (`t('browse.rateLimited')`) instead of the raw error string; whatever `result` is already cached (even stale) keeps rendering underneath either way, since `getBrowseCache` returns stale entries rather than evicting them. `ModGrid`'s skeleton branch is gated on `loadingMods` alone — a separate `!result` branch (`t('browse.loadFailed')`) covers a cold start with nothing cached where the fetch failed, which previously fell through to the skeleton branch and rendered placeholder cards forever.

**`NewsPage.tsx`** — News tab. A module-level `Map<GameId, { items, totalPages, page }>` caches the last-viewed page per game for the session (mirroring `gamePathCache`'s pattern) so switching tabs or games restores where the user left off instead of resetting to page 1. Pagination is deliberately a clone of `BrowsePage`'s numbered-page footer (`buildPages`, same active-page styling) rather than infinite scroll, to match the rest of the app: the clicked page number updates `page` state _before_ the fetch resolves (so the highlight is instant), and the previous `items`/`totalPages` are kept on screen (grid swaps to skeletons, footer never unmounts) while the new page loads — clearing them on click would hide the footer mid-transition, the opposite of `BrowsePage`'s behavior. Article links open via `api.openExternal`, never raw `<a href>`.

**`thumbnailCache.ts`** — Persistent thumbnail cache bridge. Module-level `resolved: Map<filename, thumbUrl>` deduplicates IPC calls within a session. `getLocalThumbnail(filename)` invokes `get_thumbnail` (which ensures the file exists in the disk cache, downloading if missing), then builds the URL via `convertFileSrc(filename, 'thumb')` — the custom `thumb://` protocol registered in `lib.rs`, **not** Tauri's asset protocol. The thumb protocol serves files from the thumbnails cache dir with `Cache-Control: immutable` (CDN filenames are content-unique), so the webview reuses cached decoded images across page remounts — the asset protocol sends no cache headers, which made every game/tab switch re-decode the whole grid. The `thumb:`/`http://thumb.localhost` origins must stay in `img-src` in both `csp` and `devCsp`. `getCachedThumbnailUrl(filename)` is a synchronous accessor used by `useThumbnail` to initialize state without triggering an IPC call on second render. Never call `api.getThumbnail` directly — always go through `thumbnailCache.ts`. `useModData` pre-warms thumbnails for all installed mods as mod data becomes available (both the sync cache pass and the async fetch pass).

**`hooks/useThumbnail.ts`** — Hook for thumbnail images. Initializes state synchronously from `getCachedThumbnailUrl` (local asset URL if already resolved this session); otherwise races `getLocalThumbnail` against a 50 ms timeout. A disk-cache hit wins the race, so the CDN is never touched; on timeout the CDN URL is shown **and kept for that mount** — never swap `src` after the CDN image may have painted, because the swap makes the webview re-load the image (visible flicker). The resolved local URL is still recorded so future mounts resolve synchronously. Consumers must render a placeholder for a `null` src (covers the sub-50 ms race window). The optional `full` param selects the original image instead of the 256 px small variant — see the variant policy in the `thumbnails.rs` section for which renders need which. Used in `ModCard` (full), `ModListRow` (small), and `ModDetailPage` (banner/`GalleryImage`/`LightboxImage` full, `DependencyRow` small) — never use a bare CDN URL for thumbnails. The one deliberate exception: user avatars in `ModDetailPage`'s members section load straight from `AVATAR_BASE_URL` (`users/images` on the storage CDN, `thumbnail_` prefix when `avatar_has_thumb`) — the disk cache and `thumb://` protocol only serve mod images (`mods/images`), and avatars are too small/rare to justify extending it.

**`settingsCache.ts`** — session cache for SettingsPage data: `Map<GameId, { settings: GameSettings, installedLaunchers }>`, mirroring `gamePathCache`/`installedCache`. `warmSettingsCache(game)` in `App.tsx` prefetches it whenever `activeGame` changes (and at startup), so the cache is warm before the user can reach the Settings page. `SettingsPage` sync-initializes its state from `getSettingsCache(activeGame)` in its `useState` initializers (safe because the page remounts per game via `key={activeGame}`) and revalidates in the background via `setSettingsCache`. **Render-once rule**: while `settings === null` (cold cache, prefetch not yet landed) the page renders `null` — a sub-100 ms blank reads as instant, whereas rendering provisional values that then flip reads as a glitch. The one exception is the game path, which can take seconds to detect: it shows an explicit "Detecting…" spinner placeholder (placeholder → value is acceptable; value → different value is not). **Mutation invariant**: every user mutation on the page (launcher select, debounced launch-options save, manual path pick) must call `patchSettingsCache` — otherwise the next remount restores pre-mutation values until the revalidate lands. The background revalidate only refetches `get_game_settings` (cheap settings.json read); `installed_launchers` (slow registry/manifest probe, changes only if the user installs a launcher mid-session) is reused from the session cache once warm.

**`StorageSettings.tsx`** — the Settings > Storage card (Advanced tab, below Logs). A flat `danger`-token "danger zone" card (no gradients/decoration — matches the app's `bg-warning/10 border-warning/30` warning-banner treatment) with one row per cache showing its live size and an explicit clear button (Clear images / mod info / database / news), an "All caches" row, and a "Reset settings" row. **Every** delete routes through one shared confirm dialog (a `ConfirmSpec` state object drives the single `Dialog`) so nothing deletes on one click. Sizes come from `api.getStorageUsage` (disk) plus `getModCacheSize()` (localStorage); each clear reports freed bytes inline in `text-success-text`. Clearing dispatches to the `storage.rs` commands, `clearModCache()` (mod info), and `clearResolvedThumbnails()` (drops the in-memory thumbnail-URL map so cleared images re-download); "Reset settings" calls `api.resetAppSettings`, wipes all `modrex:` localStorage keys, and reloads. `modCache.ts` gained `getModCacheSize()` (byte estimate of the four persisted caches) and `clearModCache()` (wipes the in-memory maps + their localStorage keys, cancelling the pending debounced write first so it can't re-persist); `thumbnailCache.ts` gained `clearResolvedThumbnails()`.

**`browseCache.ts`** — in-memory SWR cache for the Browse page. Keyed by `(workshopId, page, query, sort, categoryId, includeTags, excludeTags)` — the two tag-id sets are sorted and joined into the key so a tag-filtered page never collides with the same unfiltered page; the `workshopId` prefix is load-bearing: without it, switching games pollutes the other game's cache. `getBrowseCache`/`setBrowseCache` take the include/exclude tag arrays as trailing params (default `[]`). All exported functions (`getBrowseCache`, `setBrowseCache`, `getCategoriesCache`, `setCategoriesCache`, `getTagsCache`, `setTagsCache`) take `workshopId: number` as their first argument. 5-minute TTL for mod list pages; 1-hour TTL for categories and tags. `getBrowseCache` returns `{ result, stale }` or `null` — callers show the cached result immediately and skip or background-fetch based on `stale`. `categoriesCache` and `tagsCache` are each a `Map<workshopId, {..., fetchedAt}>` — one entry per game, not a singleton. Not persisted to localStorage (lives only for the process lifetime). `BrowsePage` reads the initial cache synchronously during component init so the first render already has data on return visits.

**Browse tag filter** — `TagFilter.tsx` (a `@radix-ui/react-popover` dropdown, one row per tag cycling neutral -> include -> exclude, 10 per bucket) drives `includeTags`/`excludeTags` state in `BrowsePage`, threaded through `fetchMods` into `api.listMods`'s `tags`/`block_tags` and into the browse-cache key above. The tag catalog comes from `api.listTags(workshopId)` cached via `getTagsCache`/`setTagsCache`, fetched once per game exactly like categories. The category and sort `Select`s and the Tags trigger all carry a leading `lucide` icon (`Select` gained an optional `icon` prop) so the filter row reads as one set.

**localStorage key convention** — Two scopes:

- App-level (same across games): `modrex:<key>` — e.g. `modrex:active-view`, `modrex:active-game`, `modrex:sidebar-collapsed`, `modrex:mod-cache`, `modrex:files-cache`, `modrex:links-cache`
- Game-scoped (per game): `` `modrex:${GAMES[activeGame].storageKey}:<key>` `` — e.g. `modrex:pd3:installed-view`, `modrex:pd3:browse-sort`, `modrex:pd3:collapsed-folders`

`GameId = 'pd3' | 'pd2' | 'pdth' | 'cb' | 'raid'` and `GAMES: Record<GameId, { name, shortName, workshopId, storageKey }>` are exported from `src/shared/types.ts`. `workshopId` drives modworkshop API calls; `storageKey` scopes localStorage keys. Never hardcode `'pd3'` or `853` where `activeGame` is available — use `GAMES[activeGame].*`. `BrowsePage` remounts on game change via `key={activeGame}` in `App.tsx` — browse cache and sort preference are both scoped per game.

**`deps.ts`** — dependency-warning logic shared by `ModDetailPage.tsx` and `BrowsePage.tsx` (each has its own parallel copy of the surrounding state/effects, kept in sync by hand). `collectDeps`/`isOffsiteDep`/`isLoaderDep`/`missingRequiredDeps`/`offsiteDepHost` are generic and game-agnostic. `collectDeps` sorts by the author-defined `order` field (id as tiebreak, matching modworkshop's mod-tabs sort) — the result's sequence is the author's intended install order, and `DepsTab` numbers rows from it, so never re-sort or re-group downstream. **Two different ways a "loader" dependency is represented**: SuperBLT is hosted _externally_ (no modworkshop mod page), so it's an offsite dependency detected by a `blt` substring heuristic (`isLoaderDep`) and checked via `loaderInstalled: boolean | null`. PDTHModOverrides/DAHM/UE4SS/RAID-SuperBLT are each _hosted_ on modworkshop (real mod ids — 53474/14267/47749/47771/44048/49744), so they're checked via the `loaderModIds: Record<number, boolean | null>` param instead — `missingRequiredDeps` looks the dependency's `mod.id` up there before falling back to the normal installed-list check. `isUe4ssLoaderId(gameId, id)` / `ue4ssLoaderIdsFor(gameId)` centralize the UE4SS id↔game mapping (`cb` → `[47749]`, `pd3` → `[47771, 44048]` — both real PD3 mod pages, see `ue4ss.rs`) so call sites build `loaderModIds`/dependency checks from one source instead of repeating the id list; add a new id here, not at each call site, if another UE4SS mod page is ever found. `RAID_SUPERBLT_ID` (49744) / `isRaidLoaderId(gameId, id)` are the RAID equivalents — RAID mods declare the loader as an instructs-template dependency on that page, and `loaderIdsForGame('raid')` / `buildLoaderModIds('raid', flags)` map it to the `raidSuperbltInstalled` presence flag (`api.checkRaidSuperblt`); installing it dispatches to `api.installRaidSuperblt`, never the normal mod flow.

**`formatCheck.ts`** — `SUPPORTED_FORMATS = new Set(['pak', 'zip', '7z', 'rar'])` is the single source of truth for installable formats. `.tar.gz` and `.tar.xz` are handled as a special double-extension case in the URL fallback path. `isUnsupportedFormat(type, downloadUrl?)` returns `true` when a file should show a warning before installing: checks `type` first; if undefined, infers from the URL path's file extension. Every install entry point (`BrowsePage.handleInstall`, `ModDetailPage.handleInstall`, `DownloadsTab.handleInstallFile`, `FileSelectModal.handleInstallSelected`) must call this before proceeding. When adding support for a new file format, add it to `SUPPORTED_FORMATS` here.

**`hooks/useModData.ts`** — fetches remote mod metadata for all installed mods. Signature is `useModData(installed, workshopId)` — `workshopId` is needed because the bulk refresh goes through `/games/{id}/mods`; `InstalledPage` passes `GAMES[activeGame].workshopId`. On each `installed` change, it bails early (via a sorted-id string stored in a `useRef`) when the set of installed mod IDs is unchanged — this avoids redundant re-runs on focus-refresh cycles that produce new array references. Otherwise, it first synchronously pre-populates `modData` from `getInstalledMetaEntry` (instant, no API call) and marks fresh entries in `fetchedAt` so they skip the network fetch — freshness window is `INSTALLED_META_TTL_MS` (30 min, imported from `modCache.ts` so the two stay in lockstep). Then it makes one call to `fetchInstalledModsMeta(workshopId, staleIds)` — a single batched fetch via the `ids[]` listing filter instead of fanning out one request per mod (see `modCache.ts`). Per-mod freshness is still tracked in the same `fetchedAt` `useRef` so re-renders don't re-trigger fetches. **When `installed` becomes empty (game switch), `modData`, `failedIds`, and `fetchedAt` are all reset immediately** — this prevents stale metadata from the previous game from bleeding through on the next game's render. Negative-id mods are never fetched and never added to `failedIds` (the `id >= 0` skeleton guard depends on this). Returns `modData: Map<number, Mod>`, `failedIds: Set<number>`, and `updatable: InstalledMod[]`. `updatable` deduplicates by `id` and skips any mod where the latest remote version is already installed (handles multi-file mods that share an `id`). Mods whose installed `version` is missing or `"unknown"` are never flagged updatable — an unidentified or embedded-id mod with no comparable version must not nag a perpetual false update. **`"outdated"` is a deliberate exception**: both `identify_untracked`'s `by_name()` fallback and `upgrade_negative_ids` set it (instead of `"unknown"`) specifically when a name match succeeds _after_ a SHA256 check against the index's current file already failed — that's a confirmed signal the installed bytes are stale (the mod's modworkshop file was updated since install), not just an absence of information, so it's allowed to surface as updatable rather than being suppressed.

**`hooks/installedUtils.ts`** — pure data helpers: `syntheticMod(ins)` constructs a fallback `Mod` object for negative-id and fetch-failed mods — the pattern is `apiMod ?? syntheticMod(ins)` after the skeleton guard, so negative-id mods render with their local name instead of a skeleton. `getAllModsInFolder(mods, folders, folderId)` recursively collects all mods in a folder subtree (direct children plus nested folders); used for bulk enable/disable on folder toggle. `normalizeModScopes(mods)` — for rendering only, collapses multi-folder entries for the same positive id only when some of those entries are at root (the split-install artifact where reinstalling puts some paks at root). Intentional multi-folder layouts (all entries in non-root folders) are left untouched. Called in `InstalledPage` as `renderMods = normalizeModScopes(displayMods)` before passing to `computeChildren`. `computeChildren(mods, folders, parentId, visibleFolderIds?)` builds and sorts children (mods before folders, both descending by priority) — filters out folders that have no mods in the normalized array (prevents empty auto-created folders from appearing); the optional `visibleFolderIds` set filters folders not matched by search. `groupChildren` collapses consecutive mod runs into `root-group` grid slots; `filterInstalled(mods, folders, query)` returns matching mods and the set of all ancestor folder IDs that must remain visible. `InstalledGroup = { key: string; id: number; mods: InstalledMod[] }` and `groupInstalledByIdentity(mods)` — groups by identity key (`id:N` for positive-id mods, `uid:X` for negative-id); the canonical grouping used by the health check and the mod counter. `HealthSummary` and `computeHealthSummary(mods)` — purely local health categories (missing, archiveBroken, outdated, unidentified), no network. `outdated` catches two cases: `version === 'outdated'` (SHA256 mismatch, set by Rust) and stale duplicates from `findSuspectDuplicateGroups` (bare-uid + archive-scheme uid coexisting for the same `fileId`). `healthIssueCount` in `InstalledPage` sums missing + archiveBroken + outdated + unidentified to drive the badge on the health check button — dependencies and updates are intentionally excluded from the badge.

**`hooks/useDragDrop.ts`** — all reorder-DnD state and handlers. Reordering runs on **pointer events, not HTML5 drag**: `dragDropEnabled: true` in `tauri.conf.json` (required for the drop-a-file-to-install flow — Tauri's native `onDragDropEvent`, wrapped as `api.onFileDrop` and consumed by `useFileDropInstall`/`FileDropOverlay`, is the only way to receive dropped file _paths_) disables HTML5 drag events in the webview, so the hook implements dragging itself. `onModPointerDown`/`onFolderPointerDown` arm a pending drag that starts after a 5 px movement threshold (pointer-downs on `button, a, input, textarea, select, [data-no-drag]` never arm); `pointermove` hit-tests `document.elementFromPoint` against the `data-drop-mod`/`data-drop-folder-header`/`data-drop-empty-folder`/`data-drop-child` attributes via pure `compute*DragOver` functions returning a `DropTarget`, auto-scrolling near the edges of the container behind `scrollContainerRef`; `pointerup` applies the target (`applyModReorder`/`applyDropIntoFolder`/`applyChildDrop`/`applyNestFolder`). Escape cancels, and a capture-phase click listener (removed on the next tick) swallows the click the browser fires right after a drop so it can't open the mod detail page. Mods with `location` set (secondary-target, e.g. `mod_overrides`) are blocked from cross-folder drags and into-folder drops — `computeModDragOver`'s cross-folder path, `computeFolderHeaderDragOver`, `computeEmptyFolderDragOver`, and the apply-side guards in `applyModReorder`/`applyDropIntoFolder` all check `srcMod.location`. Same-scope reordering is still permitted.

**InstalledPage component family** — `InstalledPage.tsx` is a ~230-line coordinator; the logic is split across focused files:

- `hooks/useFolderActions.ts` — all folder state (rename, delete, create, collapse, toggle-enable) and their API calls. Owns `renamingFolderId`, `deletingFolderId`, `creatingFolderParentId`, `collapsedFolders`, `loadingFolderId`.
- `hooks/useModActions.ts` — mod operation state: `loadingMod`, `reinstallProgress`, `reinstallError`, `refreshing`, `zipPickerData`. Owns `handleUninstall`, `handleEnable`, `handleDisable`, `handleReinstall`, `handleRefresh`. `handleReinstall` pre-uninstalls all missing entries before calling `installMod` — necessary because ZIP-installed paks use `{file_id}_{stem}` uids but `install_mod` creates `{file_id}`, leaving stale missing entries without this cleanup. `reinstallError` surfaces in `InstalledPage` as a dismissible banner; `clearReinstallError` resets it.
- `components/InstalledContext.tsx` — React context that `InstalledPage` provides and all descendants read via `useInstalledContext()`. Contains mod data, view mode, gamePath, `activeGame: GameId`, folder/mod action handlers, and all DnD handlers. Any new component that needs shared installed-page state should read from this context rather than adding props.
- `components/FolderSection.tsx` — renders a folder row + its contents recursively. Also exports `NewFolderInput` (used at root level in `InstalledPage` and inside folders). Reads everything from `InstalledContext`.
- `components/InstalledModItem.tsx` — renders a single mod group (list or grid variant based on `viewMode` from context). Contains the skeleton guard, `combined` InstalledMod construction, and all per-mod DnD handlers. `combined.enabled` is `mods.some(m => m.enabled)` — the group is shown as enabled if any file is enabled; only all-disabled triggers the disabled state. When `mods.length > 1`, renders a clickable "N files" badge that opens `ManageFilesModal`.
- `components/ManageFilesModal.tsx` — modal for per-file management of multi-pak mods. Uses the `Dialog` primitive (which portals into `document.body`, avoiding drag-behind from the parent draggable div). Groups files by their real `folderId` from raw `installed` (bypasses `normalizeModScopes`). Renders root-level files flat, folder groups as collapsible rows with a chevron + folder name + count + Toggle + delete button. File rows show filename + Toggle + delete. Folder-level and file-level toggle/delete operate independently. **Stale-duplicate detection**: `installedUtils.ts`'s `findSuspectDuplicateGroups` flags the exact orphan shape `install_from_zip_entry`'s pre-removal fix (above) now prevents going forward — a bare-uid entry (`uid === String(fileId)`, the `install_mod`/`install_file` scheme) coexisting with an archive-scheme entry (`uid` prefixed `"{fileId}_"`) for the same `fileId`. This is deliberately narrower than "same id, different version," which produced false positives on real mods that ship several independent files under one listing (verified live against a mod with 7 separate `.pak` files). `resolveStaleDuplicates` confirms which side is actually stale using the mod's live file `type` (pak vs zip/7z/rar) from `getCachedModFiles`, rather than guessing from install timestamps — only `ManageFilesModal` runs this (it already fetches file data), badging the stale file "Outdated" via `installed.manageFiles.staleDuplicateBadge`. `InstalledModItem`'s "N files" badge only runs the cheap structural check (no network) to decide whether to tint itself as a hint.
- `components/UpdatesModal.tsx` — owns `selectedIds`, `loadingMod`, `updatingAll`, `updateError` internally.
- `components/HealthCheckModal.tsx` — report modal opened after `runHealthCheck` in `InstalledPage`. Six tabs: dependencies, missing files, broken archives, outdated, unidentified, updates. Bulk action (tab-specific) lives in a fixed footer, never inside the scrollable list. Per-row dep "Install" calls `api.installMod` directly (UE4SS is handled entirely in Rust and never surfaces a picker sentinel). After any dep install, `handleDepInstalled` in `InstalledPage` refreshes the installed list and re-runs `checkMissingDependencies` against the fresh data — two `api.getInstalled` calls are intentional: `onRefreshInstalled` (= `refreshInstalled` in `App.tsx`) updates App state but returns nothing, so a second local fetch (~2ms filesystem) provides the fresh list for the dep re-check. `missingDeps` is a snapshot prop; the re-check via `onDepInstalled` is the only way to update it while the modal is open.
- `components/DeleteFolderModal.tsx` — stateless confirm dialog; `onConfirm`/`onCancel` as props.
- `components/ErrorBoundary.tsx` — class component wrapping the entire app; catches render errors, logs them via `@tauri-apps/plugin-log`, and shows a minimal crash screen.

**Skeleton guard**: render a skeleton only when `!apiMod && !failedIds.has(id) && id >= 0`. The `id >= 0` is load-bearing — negative-id (unrecognized) mods are never fetched and never added to `failedIds`, so without it they render as permanent skeletons.

**Confirm dialogs**: never use `window.confirm`. All modals use `components/Dialog.tsx` — a thin wrapper around `@radix-ui/react-dialog` that provides focus trap, scroll lock, Escape key, and portal rendering. Pass `open`, `onOpenChange`, `title` (screen-reader only), and a `className` with width/height constraints. The `Dialog` component carries `text-text` on its Content so portaled children inherit the correct text color — any new portaled component must do the same. Do not use `fixed inset-0 z-50` manual overlays or `createPortal` for modals.

**ModDetailPage loading model**: three distinct loading states. (1) `loading` — full-page spinner, true only when no mod data at all (cold cache, no `initialMod`). Sync-initialized from `getModCacheEntry(modId)` and the `initialMod` prop — starts `false` when either is available. (2) `filesLoading` — Downloads-tab-only spinner, true until files + links resolve. Sync-initialized from `getFilesCacheEntry(modId)` — starts `false` when the files cache is warm. (3) `error` — hides the entire page; only set on mod-data-load failure, never on files/links failure. `fetchData` fires two independent parallel chains: `getCachedMod` sets `loading = false` when resolved; `Promise.all([getCachedModFiles, getCachedModLinks])` sets `filesLoading = false` when resolved. This means the header and description render as soon as mod data is available, without waiting for files/links. `initialMod?: Mod` prop accepts the partial `Mod` object from the browse list (missing `images`, `banner`, `dependencies`, `instructs_template`, `tags`, `changelog`) — enough for the header to render. Those fields arrive when `fetchData` completes and `setMod` replaces the seed. `installError` is a separate dismissible banner that coexists with the page content — never conflate it with `error`.

**ModDetailPage error states**: `error` (set by `fetchData` mod chain) hides the entire page content — only set it on mod-data-load failures. `installError` is the install-operation error — a dismissible banner that coexists with the page content. Install handlers (`handleInstall`, the `NonPakConfirmModal.onConfirm` callback) must be `async` and `await doInstall()` inside a `try/catch` that calls `setInstallError`; omitting the `await` turns errors into silent unhandled rejections. `doInstall` clears `installError` at entry so it resets automatically on each new attempt.

**DepsWarningModal on the detail page**: `onGotIt` only dismisses the modal and records the dismissal — it does not re-call `doInstall`. The user must click Install again. This is intentional.

**Archive install flow**: `ZipPickerModal` handles multi-pak archives (ZIP, 7z, tar.gz, tar.xz, RAR) — entries default to your previously-installed variant(s) when this is an update (matched by filename against the existing install, since the new file's id never matches the old one) or to every entry on a fresh install; installs sequentially, calls `api.deleteTempFile(zipPath)` after all entries finish. The picker's two pieces of reusable logic — `computeAutoUpdateSelection` (the filename-matching above) and `installZipPickerEntries` (the actual install loop, factored out so it can run without ever showing the modal) — are both exported from `ZipPickerModal.tsx`. `UpdatesModal` calls them directly on a `ZIP_MULTI_PAK` sentinel: if every previously-installed file variant has a filename match in the new archive, it silently reinstalls just those files and never shows the picker at all — only a genuinely ambiguous case (no prior install, or no filename match) falls back to opening it. `UpdatesModal`'s "Update Selected" batch runs through a `queueRef`-backed `processQueue` loop: hitting a sentinel that does need a picker (this one or any of the three siblings below) pops that mod off the queue, opens the modal, and pauses; the modal's `onClose` calls `processQueue` again to resume with the next queued mod, so a multi-mod batch update completes on one click even when one mod along the way needs a manual decision. When the archive is "structured" (entries span more than one directory after stripping a common wrapper prefix), `ZipPickerModal` renders folder groups and automatically creates app folders per subdirectory before installing — `getRequiredDirs` returns all needed paths shallowest-first so parents are created before children; `stripWrapperPrefix` keeps flat-only wrappers intact (their name becomes an app folder) and only strips the prefix when entries mix root-level paks and subdirectories. Folder auto-creation is skipped when `payload.targetTag` is set — secondary-target mods can't be placed in primary-target app folders. **Also skipped for Crime Boss pak entries** (`gameId === 'cb' && payload.entryKind !== 'dir'`, via `isCrimeBossPakArchive`): `install_from_zip_entry` always re-synthesizes its own `Content/Paks/WindowsNoEditor` skeleton for CB pak entries via `extract_entry_into_crimeboss_skeleton` regardless of the entry's original path inside the zip (see the Crime Boss domain facts below), so a CB pak archive whose entries all share one ModKit-wrapped directory (a common shape — multiple pak variants packaged together by the official ModKit) is never treated as "structured"; otherwise the modal would recreate that wrapper as real app folders and the backend would nest its own skeleton inside them, doubling `Content/Paks/WindowsNoEditor`. CB directory entries (`entryKind === 'dir'`, UE4SS sub-mods or host-pack candidates) are unaffected and still get normal structured handling. The Rust command `install_from_zip_entry` (name kept for backwards compat) uses `extract_entry` internally and dispatches by magic bytes, so it handles all supported archive formats. `parseZipMultiPak(errStr)` is a utility exported from `ZipPickerModal.tsx` used by every install entry point to detect and parse the `ZIP_MULTI_PAK:{...}` error string — the wire protocol name is unchanged even for non-ZIP archives. `ZipMultiPakPayload` carries `targetTag?: string` plus an optional parallel `entryTags?: (string|null)[]`; when `entryTags` spans more than one target (a mixed mods+overrides modpack) `ZipPickerModal` groups entries by destination and installs each with its own `locationTag` and no app-folder creation. Three sibling sentinels are handled the same way (parse in the catch, render a modal): `parseHostModPack`/`HostPackModal` (`HOST_MOD_PACK` — install a content pack into its host mod via `installHostPack`, or offer to install the host first when absent), `isUnrecognizedArchive`/`UnrecognizedArchiveModal` (`UNRECOGNIZED_ARCHIVE` — show the mod's instructions instead of mislaying the files), and `parseCbFlatArchive`/`CrimeBossFlatArchiveModal` (`CB_FLAT_ARCHIVE` — confirms installing a Crime Boss archive with no enclosing folder, since every entry sits at the zip root and there's only one possible destination). All four are wired into `BrowsePage`, `ModDetailPage`, its `DownloadsTab`, the Installed-page reinstall flow (`useModActions.handleReinstall` → modals rendered by `InstalledPage`), and the Updates modal (`UpdatesModal`). `FileSelectModal` handles ZIP\*MULTI_PAK inline: it pauses its install loop (via a Promise resolved by `zipResolveRef`), renders `ZipPickerModal` after its own main div (so it appears on top at the same `z-50`), then resumes with the next file when ZipPickerModal closes. When adding a new install entry point that calls a Rust install command, handle **all four** sentinels in the catch block (`parseZipMultiPak`, `parseHostModPack`, `parseCbFlatArchive`, `isUnrecognizedArchive`) — missing one surfaces a raw `\**:{...}`string as an error (this is how the reinstall path regressed, and later the Updates modal, which showed a generic "Update failed" for any mod whose latest file is a multi-pak archive until it was wired up too).`InstalledMod.archiveBroken`(previously`zipArchive`) is set by `mark_archive_files`when an installed pak file is detected as an archive by magic bytes; persisted in the state file and cached across launches — shown as a warning badge in`ModCard`and`ModListRow`.
